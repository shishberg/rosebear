# Custom Dual-Mode 36-Key Split Keyboard: Hardware/Firmware Handoff

## Project goal

Build a fully custom **36-key split keyboard**, with **18 keys per half**, that can operate in two distinct modes:

1. **Home / desk mode**

   * USB connection to the host computer.
   * Wired connection between keyboard halves.
   * Per-key RGB LEDs enabled.
   * Battery drain is not a concern because the keyboard is externally powered.

2. **Office / portable mode**

   * Bluetooth/BLE connection to the host computer.
   * BLE connection between the two keyboard halves.
   * Per-key LEDs disabled.
   * No external cables between host or halves.
   * Battery life matters.

The keyboard does not necessarily need seamless hot-switching between modes on day one. The priority is to avoid a hardware design that makes either mode impossible later.

A reset/reboot to change modes is acceptable initially. Runtime mode switching can be treated as a later stretch goal.

## Layout assumption

The keyboard is a **36-key split**, with **18 keys per half**.

This probably does not materially change the MCU choice, but it helps guide the build:

* Low matrix pin pressure.
* Small PCB per half.
* Easier to reserve spare GPIOs.
* Lower LED count than larger keyboards.
* More realistic battery operation in portable mode.
* More room in the pin budget for UART, cable detect, LED control, battery sense, and debug features.

A typical matrix might be something like:

* 3 rows × 6 columns per half, or
* another 18-key-per-half arrangement depending on physical layout.

Because the layout is small, do not aggressively optimise away useful GPIOs. Prefer a simple, debuggable matrix and preserve spare pins.

## Recommended platform

Use **nRF52840 on both halves**.

This remains the recommended hardware platform because it gives the best long-term balance:

* Native USB device support.
* Strong BLE support.
* Good fit for battery-powered keyboards.
* Mature keyboard ecosystem.
* Enough GPIO for a 36-key split plus LEDs, UART, cable detect, and debug.
* Suitable for custom Rust/Embassy/RMK work.

However, RMK’s current stock support has an important limitation:

> RMK appears to support BLE split on nRF52840, but stock serial split code generation currently appears to be implemented for RP2040, not nRF52840.

This means nRF52840 is not the lowest-effort stock-RMK platform for wired serial split today. It is still a good hardware choice if we are prepared to implement or adapt nRF52 full-duplex UART serial split support in RMK.

## Key RMK support finding

RMK’s documentation describes wired split in generic serial terms, but the current macro implementation appears to panic for non-RP2040 serial split initialisation with an error like:

```rust
panic!("Serial for chip {:?} isn't implemented yet", chip.series)
```

For nRF52840, this means:

| Mode                                               |          Stock RMK confidence |
| -------------------------------------------------- | ----------------------------: |
| BLE host + BLE split                               |                          High |
| USB host + BLE split                               |                          High |
| USB host + wired serial split                      | Not currently stock-supported |
| One firmware that auto-selects BLE or serial split |                   Custom work |
| Full-duplex UART serial split after RMK changes    |                     Plausible |
| One-wire/TRRS-style serial split                   |        Avoid for this project |

The project should assume that **nRF52840 wired serial split requires custom RMK work**.

## Why full-duplex UART changes the risk

The earlier concern came partly from TRRS-style keyboard conventions, where the inter-half link is often a constrained single-wire serial connection.

For this project, we are designing the hardware from scratch. Therefore, we should avoid single-wire serial entirely and use **full-duplex UART** between halves.

Recommended wired split signals:

```text
central TX  → peripheral RX
central RX  ← peripheral TX
GND         ↔ GND
wired power → peripheral wired/LED rail
```

This avoids:

* Single-wire bus arbitration.
* Half-duplex direction control.
* RP2040 PIO-style tricks.
* Open-drain signalling complexity.
* TRRS hot-plug shorting assumptions.
* “Which side is driving the line?” bugs.

The RMK work then becomes much more bounded: add nRF52 support for a normal async UART byte stream and feed that into RMK’s existing serial split machinery.

## Recommended inter-half connector

Use a dedicated inter-half connector with enough conductors for full-duplex serial, power, detection, and future expansion.

Minimum useful signals:

| Signal                          | Purpose                                              |
| ------------------------------- | ---------------------------------------------------- |
| GND                             | Shared reference                                     |
| Wired power / VBUS / 5V         | Powers peripheral half and LED rail in wired mode    |
| UART TX central → peripheral RX | Wired split data                                     |
| UART RX central ← peripheral TX | Wired split data                                     |
| Cable detect                    | Lets firmware choose wired mode at boot              |
| Spare GPIO                      | Future reset, boot, wake, interrupt, or debug signal |

That is a **minimum of 6 conductors**. Prefer **8+ conductors** if the connector allows it.

### Connector options

Good options:

| Connector                         | Notes                                                                                                              |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| USB-C as dumb interconnect        | Compact, reversible, many conductors, easy cables; must be clearly marked and protected because it is not real USB |
| JST-GH / JST-SH / Molex PicoBlade | Electrically safer, keyed/locking, less likely to be misused                                                       |
| RJ12 / RJ45                       | Cheap cables, many conductors, robust; physically larger                                                           |
| Magnetic pogo / custom dock       | Nice UX, more mechanical complexity                                                                                |

Avoid TRRS unless compatibility with existing keyboard conventions matters. Since this is a from-scratch design, TRRS is not worth the limitations.

## Proposed inter-half pinout concept

Example 8-conductor inter-half cable:

| Pin | Signal                    | Notes                                    |
| --: | ------------------------- | ---------------------------------------- |
|   1 | GND                       | Ground reference                         |
|   2 | GND                       | Second ground for robustness             |
|   3 | 5V wired power            | Powers peripheral in wired mode          |
|   4 | LED power or switched 5V  | Optional separate LED rail               |
|   5 | UART TX A→B               | Central TX to peripheral RX              |
|   6 | UART RX A←B               | Peripheral TX to central RX              |
|   7 | Cable detect / mode sense | Pulled to known state when cable present |
|   8 | Spare GPIO                | Future reset/wake/debug/mode line        |

The exact pinout should be chosen alongside connector and power-path design.

If USB-C is used as the physical connector, do not pretend this is USB protocol. Treat it as a keyed multi-pin connector and add protection/marking accordingly.

## LED power design

Do not rely only on firmware to disable LEDs in portable mode.

Design the LED power rail so it is physically unavailable from battery, or at least hardware-gated off by default.

Recommended power domains:

| Rail            | Source                                              | Purpose        |
| --------------- | --------------------------------------------------- | -------------- |
| MCU/matrix rail | Battery or USB                                      | Keyboard logic |
| LED rail        | Wired power only, or load-switched from wired power | Per-key LEDs   |
| LED data        | MCU GPIO through appropriate resistor/protection    | LED control    |

Key safety property:

> In portable mode, the LEDs should not be able to drain the battery even if firmware crashes, a GPIO floats, or the LED driver misbehaves.

Possible implementation:

1. LED rail is powered only from wired/inter-half power.
2. LED rail is controlled by a load switch or MOSFET.
3. The load switch defaults off.
4. Firmware only enables the LED rail when wired power is detected.
5. LED data line has protection to avoid phantom-powering LEDs when the LED rail is off.

Because this is only a 36-key board, the LED current budget is smaller than on a large keyboard, but still large enough to dominate battery life if accidentally enabled.

## Power architecture

Each half should be able to run from battery in portable mode.

In wired mode:

* The central half receives USB power from the host.
* The peripheral half receives wired power through the inter-half connector.
* LED power is available only in wired mode.
* The peripheral half should not need to draw LED current from its battery.

Power-path design must avoid unsafe backfeeding:

* USB/wired power should not backfeed into a battery incorrectly.
* Peripheral battery should not try to power the LED rail.
* A powered central half should not accidentally charge or feed the peripheral battery unless the design explicitly supports that.
* The keyboard should behave safely if one half has a battery and the other does not.

## Firmware strategy

### Phase 1: prove BLE mode

Build or adapt RMK firmware for:

* nRF52840 central.
* nRF52840 peripheral.
* BLE host connection.
* BLE split connection.
* LEDs disabled.

Success criteria:

* Both halves scan keys.
* Central reports to host over BLE.
* Reconnect behaviour is acceptable.
* Battery current is plausible.
* Peripheral half works independently from its own battery.

### Phase 2: prove USB host + BLE split

Build a mode where:

* Central talks to host over USB.
* Halves still communicate over BLE.
* LEDs remain disabled or test-only.

This is not the final home mode, but it validates the USB host path and RMK’s documented “USB host while BLE split” behaviour.

Success criteria:

* Central reports over USB.
* Peripheral half still contributes keys over BLE split.
* No obvious conflict between USB host output and BLE split.

### Phase 3: implement/prove nRF52840 full-duplex serial split

This is the key custom RMK work.

Goal:

* Central talks to host over USB.
* Central talks to peripheral over full-duplex UART.
* Peripheral sends key state over UART.
* LEDs can be enabled in wired mode.

Likely implementation work:

1. Add an nRF52/nRF52840 branch to RMK’s serial split initialisation macro.
2. Instantiate an Embassy nRF UARTE/BufferedUarte peripheral.
3. Bind the appropriate UARTE interrupt.
4. Allocate RX/TX buffers correctly.
5. Configure TX/RX pins from RMK config.
6. Ensure the resulting serial object satisfies RMK’s async read/write trait bounds.
7. Test both central and peripheral builds.

Expected difficulty:

| Goal                                              |       Rough effort |
| ------------------------------------------------- | -----------------: |
| Hack it until it compiles                         |          0.5–1 day |
| Get UART bytes moving between two nRF52840 boards |          0.5–1 day |
| Make RMK serial split work reliably               |           2–5 days |
| Make it clean/upstreamable                        |          1–2 weeks |
| Add robust runtime mode switching                 | Later stretch goal |

### Phase 4: boot-time mode selection

Once BLE split and serial split both work separately, attempt a single firmware that chooses mode at boot.

Boot logic concept:

```text
if inter_half_cable_present && usb_or_wired_power_present {
    start USB host output
    start serial split
    enable LED power
} else {
    start BLE host output
    start BLE split
    keep LED rail disabled
}
```

Mode change can require reset/reboot. That is acceptable.

### Phase 5: optional hot switching

Hot switching is a stretch goal and should not drive the first hardware revision.

Potential challenges:

* Stopping BLE split cleanly.
* Starting serial split after boot.
* Reinitialising host output.
* Resynchronising split state.
* Avoiding stuck keys during transition.
* Handling cable insertion/removal.
* Managing LED rail power safely.
* Preserving BLE pairing and reconnect behaviour.

## Hardware design principles

### Preserve options

Because the software path may evolve, the PCB should preserve flexibility:

* Route full-duplex UART between halves.
* Add cable detect.
* Add wired power detect.
* Add LED power enable/sense.
* Expose SWD on both halves.
* Expose reset/boot access on both halves.
* Leave spare GPIOs.
* Keep the matrix simple.
* Avoid sharing critical debug or UART pins with awkward hardware.

### Do not over-optimise the matrix

With only 18 keys per half, GPIO pressure should be manageable.

Prefer a simple matrix over clever pin saving. For example:

* A straightforward 3×6 matrix per half is easy to reason about.
* It leaves enough pins for UART, LEDs, battery sense, cable detect, and debug.
* It reduces firmware bring-up complexity.

### Avoid fragile interconnect assumptions

Do not build the first revision around:

* Single-wire serial.
* TRRS hot-plug behaviour.
* USB protocol between halves.
* USB-C Power Delivery.
* Automatic hot switching.
* Peripheral half being powered through accidental paths.
* Firmware-only LED disable.

## Risk register

| Risk                                               |   Severity | Mitigation                                                  |
| -------------------------------------------------- | ---------: | ----------------------------------------------------------- |
| RMK stock serial split does not support nRF52840   |       High | Plan to implement nRF52 full-duplex UART serial split       |
| nRF52 UARTE integration takes longer than expected |     Medium | Prototype on dev boards before PCB                          |
| Runtime mode switching is too hard                 |     Medium | Accept boot-time mode selection or separate firmware builds |
| Hot switching is too hard                          |        Low | Treat as stretch goal                                       |
| LED rail drains battery                            |       High | Hardware-gate LED power; wired-power-only LED rail          |
| USB-C inter-half connector is mistaken for USB     |     Medium | Use keyed connector or add protection/clear labelling       |
| Peripheral power path backfeeds battery/USB        |       High | Use proper power-path/load-switch/ideal-diode design        |
| BLE performance or reconnect behaviour is poor     |     Medium | Prototype early with real batteries/enclosure assumptions   |
| Too few GPIOs                                      | Low/medium | 36-key layout gives margin; reserve pins early              |
| Debug access awkward after assembly                |     Medium | Add accessible SWD pads, reset, boot, test pads             |

## Early prototype checklist

Before committing to a full custom PCB, build a proof of concept with dev boards.

### Prototype A: BLE split

Goal:

* Two nRF52840 boards.
* RMK BLE split.
* Host over BLE.
* No LEDs.

Success criteria:

* Both halves scan keys.
* Central reports to host over BLE.
* Battery behaviour is plausible.

### Prototype B: USB host + BLE split

Goal:

* Same BLE split setup.
* Central plugged into USB host.

Success criteria:

* Central reports to host over USB.
* Inter-half remains BLE.
* Confirms the USB host path on the central half.

### Prototype C: raw nRF52840 UART

Goal:

* Two nRF52840 boards.
* Full-duplex UART between them.
* Independent of full RMK split at first if needed.

Success criteria:

* Bytes move reliably both directions.
* Chosen TX/RX pins work.
* Embassy UARTE setup is understood.
* Buffer and interrupt requirements are clear.

### Prototype D: RMK USB host + nRF52840 serial split

Goal:

* Custom RMK changes.
* Central reports to host over USB.
* Halves communicate over full-duplex UART.

Success criteria:

* Both halves scan keys.
* Split state is reliable.
* No panic from missing serial implementation.
* Firmware structure is clean enough to keep iterating.

### Prototype E: LED power gating

Goal:

* Add representative per-key LED chain or LED load.
* Power LEDs only from wired power.

Success criteria:

* LEDs work in wired mode.
* LEDs remain physically unpowered in battery mode.
* MCU remains stable when LED rail is off.
* LED data line does not phantom-power LED rail.

### Prototype F: boot-time mode selection

Goal:

* Detect wired cable/power at boot.
* Choose wired or wireless mode.

Success criteria:

* Boot with cable: USB host + serial split + LEDs available.
* Boot without cable: BLE host + BLE split + LEDs disabled.
* Reset is acceptable for mode changes.

## Recommended first concrete decision

Proceed with an **nRF52840-based 36-key split design**, but assume that wired serial split support must be implemented or adapted in RMK.

The most important technical proof-of-concept is:

> Can two nRF52840 boards run RMK with USB-to-host and full-duplex UART serial between halves?

If yes, the hardware platform is likely safe.

If no, decide whether to:

1. Continue implementing nRF52 serial split support in RMK.
2. Switch to RP2040/Pico W for stock RMK serial split support.
3. Drop fully wired inter-half mode and accept USB-to-host plus BLE-between-halves.

## Current recommendation

Use:

* **nRF52840** on both halves.
* **36-key layout**, 18 keys per half.
* **BLE split** for portable mode.
* **Full-duplex UART serial split** for wired mode.
* **USB host connection on central half**.
* **Dedicated inter-half connector** carrying power, ground, UART TX/RX, cable detect, and spare GPIO.
* **Hardware-gated LED power rail** unavailable in portable mode.
* **Boot-time mode selection** as the realistic custom firmware target.
* **Hot switching** only as a later stretch goal.

This design keeps both desired modes open without relying on single-wire TRRS assumptions or pretending that stock RMK already supports nRF52840 serial split.
